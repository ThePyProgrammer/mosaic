```latex
\subsection{MAGiC-SLAM}
\label{sec:systems:magic-slam}

MAGiC-SLAM is one of the clearest public baselines for online multi-agent Gaussian SLAM \citep{magic_slam_2025}.  The system targets multiple RGB-D agents operating concurrently in an unknown scene.  Each agent maintains local tracking and mapping state over a Gaussian scene representation, while a server-side component stores agent features and submaps, detects cross-agent loop closures, estimates loop constraints, optimizes a pose graph, and merges per-agent submaps into a globally consistent Gaussian map.  Its architectural pattern is therefore a centralized agent--server fusion pipeline: local Gaussian submaps are produced at the edge, and global consistency is recovered through loop detection, pose-graph optimization, and map merging rather than by treating all observations as a single monolithic stream.

The reported modality is RGB-D, with experiments on ReplicaMultiagent and AriaMultiagent-style sequences.  Benchmark evidence is relatively strong compared with newer systems: reported ReplicaMultiagent tracking accuracy is approximately 0.27 cm average ATE RMSE, with rendering around 34.26 dB PSNR, 0.97 SSIM, 0.12 LPIPS, and 1.30 cm Depth L1 in the extracted tables.  The same evidence reports per-agent mapping and tracking around 0.71 s and 0.69 s, global map merging around 167 s, peak GPU memory around 1.12 GiB, and a submap disk size of roughly 54 MB.  These numbers should not be collapsed into a single real-time rate because tracking, mapping, and global merging are distinct phases.

Source availability is good for a research prototype: a public GitHub repository is available, with runnable-looking scripts, dataset configurations, CUDA/PyTorch dependencies, and an MIT license text with a caveat for third-party Inria Gaussian Splatting components.  The main caveat is engineering integration risk.  MAGiC-SLAM is CUDA/native-extension-heavy research code, assumes dataset-specific layouts and multi-GPU execution for ideal multi-agent operation, and exposes little evidence about actual communication bandwidth.  It is best cited as a mature public implementation and as evidence for a server-mediated submap/loop-closure architecture, not as a clean library dependency.

\paragraph{System profile.}
\textbf{Modality:} RGB-D multi-agent streams.  \textbf{Map representation:} per-agent/local 3D Gaussian submaps merged into a global Gaussian map.  \textbf{Fusion architecture:} centralized server with feature/submap exchange, loop detection, pose-graph optimization, and global map merge.  \textbf{Source availability:} public code; MIT text with third-party 3DGS caveat.  \textbf{Benchmark highlights:} ReplicaMultiagent average ATE around 0.27 cm; reported peak GPU memory 1.12 GiB; submap disk size 54 MB; global merge about 167 s.  \textbf{Caveats:} RGB-D only in the reported setup; limited bandwidth reporting; research-code dependencies and GPU assumptions.

\subsection{MAC-Ego3D}
\label{sec:systems:mac-ego3d}

MAC-Ego3D is a functional target-class system for this survey if the inclusion criterion is collaborative online ego-motion plus Gaussian mapping, even though the title emphasizes ego-motion and photorealistic reconstruction rather than ``SLAM'' \citep{mac_ego3d_2025}.  The system uses a shared 3D Gaussian representation for real-time multi-agent RGB-D reconstruction.  Each agent builds, aligns, and refines local Gaussian maps, while consensus mechanisms enforce consistency within and across agents.  The distinctive contribution is Gaussian consensus: intra-agent consensus maintains coherence among nearby Gaussians within a local map, and asynchronous inter-agent consensus aligns, optimizes, and fuses local maps into a global model.

Architecturally, MAC-Ego3D is the strongest example of a distributed or consensus-oriented fusion pattern among the public candidates.  Unlike a purely server-merged design, the method is described around parallelized intra-agent and inter-agent Gaussian consensus.  This makes it especially relevant for surveys concerned with communication schedules, stale local maps, and asynchronous global alignment.  The reported modality is RGB-D, with evaluations on Multi-Agent Replica and 7-Scenes.  Extracted benchmark tables report approximately 0.14 cm average ATE RMSE on Multi-Agent Replica, dense mapping quality around 40.04 dB PSNR, 0.977 SSIM, 0.050 LPIPS, and 0.74 mm Depth L1, plus per-frame times around 0.02 s for tracking and 0.05 s for mapping.  Communication is reported mainly through intervals such as $T_{\mathrm{comm}}$, not through bytes or bandwidth.

Source availability is strong: the repository is public, MIT-licensed, and contains code, configurations, a Dockerfile, requirements, tracking/mapping modules, rendering/model utilities, and benchmark scripts.  The caveat is classification rather than availability.  A strict bibliography that only counts papers branded as ``SLAM'' may mark MAC-Ego3D as near-target, but a functional taxonomy should include it because it performs multi-agent online ego-motion and globally fused Gaussian reconstruction.  As with the other open systems, it remains research code with 3DGS/CUDA-style dependencies and should be interpreted as a backend/reference system rather than a lightweight software component.

\paragraph{System profile.}
\textbf{Modality:} RGB-D.  \textbf{Map representation:} unified/shared 3D Gaussian splat representation with local agent maps.  \textbf{Fusion architecture:} distributed/asynchronous Gaussian consensus with intra-agent and inter-agent consistency.  \textbf{Source availability:} public MIT code.  \textbf{Benchmark highlights:} Multi-Agent Replica average ATE around 0.14 cm; PSNR around 40.04 dB; reported 0.02 s tracking and 0.05 s mapping per frame.  \textbf{Caveats:} not titled as a SLAM paper; communication reported as intervals rather than bandwidth; code is research-oriented and GPU-dependent.

\subsection{CoKo-SLAM}
\label{sec:systems:coko-slam}

CoKo-SLAM, or Compact Keyframe-Optimized Multi-Agent Gaussian Splatting SLAM, targets communication-efficient RGB-D multi-agent Gaussian SLAM \citep{coko_slam_2026}.  The system follows a centralized architecture in which robot-side agents construct local Gaussian maps and send compact map/keyframe information to a server.  The server merges and optimizes local maps, removes redundant 3D Gaussians, and performs loop closure without requiring an initial relative-pose guess.  Two reported variants use either rendered-depth information derived from Gaussians or lightweight camera-depth images for alignment and pruning.

The primary map representation is a compacted 3D Gaussian map augmented by keyframe features or summaries.  This makes CoKo-SLAM important for multi-robot settings where the central question is not only map quality but also what should be transmitted: raw images, point clouds, dense maps, compact Gaussians, keyframes, or descriptors.  The paper-level evidence claims that compacting and transmitting Gaussian/keyframe representations reduces transmitted data by roughly 85--95\% relative to baselines while preserving reconstruction fidelity.  Public reports mention ReplicaMultiagent and AriaMultiagent configurations, but exact benchmark values should be cited conservatively unless taken from the final paper tables.

A public implementation exists at the author repository, and the README states that it is based on MAGiC-SLAM.  The repository includes runnable-looking scripts, configurations, mapping/tracking modules, loop detection, pose-graph components, and an MIT license text with the same third-party Gaussian Splatting caveat as MAGiC-SLAM.  However, the code is young and has reproducibility red flags: the dependency file is misspelled as \texttt{requirments.txt} in observed sources, while instructions reference \texttt{requirements.txt}, and the frozen dependencies include absolute local filesystem paths for several CUDA/encoding/rasterization components.  CoKo-SLAM is therefore best used as evidence for a compact communication and centralized fusion design, while source-level reuse should be treated cautiously.

\paragraph{System profile.}
\textbf{Modality:} RGB-D; rendered-depth and camera-depth modes are reported.  \textbf{Map representation:} compacted 3D Gaussian maps plus keyframe/features or summaries.  \textbf{Fusion architecture:} centralized server for map merge, compaction, loop closure, and optimization.  \textbf{Source availability:} public code; MIT text with third-party caveat; dependency hygiene issues.  \textbf{Benchmark highlights:} claimed 85--95\% lower transmitted data; evaluated/configured for ReplicaMultiagent and AriaMultiagent.  \textbf{Caveats:} young implementation; install instructions appear inconsistent; exact benchmark table values should be verified against the primary paper.

\subsection{CoMA-SLAM}
\label{sec:systems:coma-slam}

CoMA-SLAM is a distributed multi-agent Gaussian SLAM system whose representation should be distinguished from conventional 3D radiance splats: the available AAAI evidence describes 2D Gaussian surfels and geometric consistency \citep{coma_slam_2026}.  The system is relevant to a broad ``Gaussian map'' survey because it addresses the same collaborative mapping problem: multiple agents maintain submap-centric updates, close intra- and inter-agent loops, and perform distributed keyframe optimization to recover a consistent shared representation.  Its claimed architecture avoids simply sending all data to a central server and instead emphasizes distributed optimization, robust initialization, and communication-efficient map updates.

The precise sensor modality is less clearly documented in the fetched summary than for RGB-D systems such as MAGiC-SLAM or CoKo-SLAM.  Repository configurations mention ReplicaMultiagent and AriaMultiagent-style data, while the paper summary emphasizes Gaussian scene representation, 2D Gaussian surfels, distributed keyframe optimization, submap-centric updates, and geometric consistency.  Reported benchmark evidence from the AAAI/project-level sources includes improved pose, rendering, and geometric consistency, with a headline claim of approximately 99.8\% lower communication bandwidth than centralized methods.  Because exact tables were not fully extracted, this number should be cited as a paper claim rather than as an independently audited benchmark.

A public repository exists and contains implementation-looking code, including SLAM runners, visualization scripts, agent/server modules, mapping/tracking, pose-graph adaptation, loop-detection modules, LCM message definitions, and vendored \texttt{gsplat} components.  The main source-availability caveat is licensing: no top-level license was found, and a vendored third-party license does not license the whole repository.  For a survey, CoMA-SLAM should be included as a Gaussian-surfel, distributed, low-communication collaborative SLAM system, but with explicit caveats about modality visibility, top-level license absence, and the representation difference from standard 3D Gaussian Splatting radiance maps.

\paragraph{System profile.}
\textbf{Modality:} not cleanly visible in fetched primary summaries; configs indicate ReplicaMultiagent/AriaMultiagent-style datasets.  \textbf{Map representation:} 2D Gaussian surfels / Gaussian scene representation.  \textbf{Fusion architecture:} distributed submap-centric updates, intra/inter-loop closure, and distributed keyframe optimization.  \textbf{Source availability:} public repository, but no top-level license found.  \textbf{Benchmark highlights:} paper/page claim of 99.8\% lower communication bandwidth and improved pose/rendering/geometric consistency.  \textbf{Caveats:} not conventional 3DGS radiance splats; exact modality and full benchmark tables require verification; unlicensed repository limits reuse.

\subsection{HAMMER}
\label{sec:systems:hammer}

HAMMER is a paper/project-page target-class system for heterogeneous multi-robot semantic Gaussian Splatting \citep{hammer_2025}.  Its motivation differs from RGB-D-only collaborative SLAM systems: heterogeneous robots and sensing devices stream data to a server, where local SLAM poses and visual/perceptual observations are aligned into a common frame and used to train or update a shared metric-semantic 3D Gaussian map.  The central architectural primitive is not merely loop closure but global frame alignment without prior robot positions or prior relative pose knowledge.  The shared map also carries semantic information, including open-vocabulary/CLIP-style codes, making HAMMER especially relevant for agent-facing map-query and semantic-posterior interfaces.

The modality should be described conservatively as heterogeneous image/perception streams plus local SLAM poses, rather than as a single clean RGB-D API.  Extracted evidence mentions asynchronous robot data streams, ROS-style communication, local SLAM outputs, Aria glasses, ground robots, ZED stereo, fisheye RGB, point clouds/depth, and onboard localization sources.  Benchmark evidence is unusually broad for the field: ReplicaMultiAgent experiments use two robots, and hardware examples include two Aria glasses plus one or two ground robots.  Reported Replica averages include roughly 37.28 dB PSNR, 0.95 SSIM, 0.09 LPIPS, and 1.47 cm Depth L1.  Runtime evidence includes online map updates around 15--38 ms/frame, inter-robot alignment around 36 s per new robot, and per-device streaming around 30--35 Mbps, with depth responsible for most of that bandwidth.

The principal caveat is source availability.  HAMMER is target-class by paper and project-page claims, but no public implementation was found in the available repository searches; the project page marked code as coming later or exposed only a placeholder link.  The website license, if any, should not be treated as a software license.  Survey prose should therefore separate architectural evidence from implementation evidence: HAMMER is a strong paper-only or project-page-only reference for heterogeneous multi-robot semantic Gaussian mapping, but not an auditable backend at present.

\paragraph{System profile.}
\textbf{Modality:} heterogeneous robot/device image and perception streams plus local SLAM poses; depth/point clouds/stereo appear in hardware evidence.  \textbf{Map representation:} shared metric-semantic 3D Gaussian Splatting map with open-vocabulary semantic codes.  \textbf{Fusion architecture:} server-based online collaborative mapping with global frame alignment and no prior relative robot poses.  \textbf{Source availability:} no public code found; project-page/paper evidence only.  \textbf{Benchmark highlights:} Replica average PSNR around 37.28 dB; online updates about 15--38 ms/frame; alignment about 36 s per new robot; 30--35 Mbps per device in hardware tests.  \textbf{Caveats:} implementation not auditable; exact sensor API unavailable; do not overstate loop-closure/pose-graph mechanics unless citing the full paper.

\subsection{GRAND-SLAM}
\label{sec:systems:grand-slam}

GRAND-SLAM is a large-scale multi-agent RGB-D Gaussian SLAM system focused on global consistency through local optimization, loop closure, and pose-graph optimization \citep{grand_slam_2025}.  It should be described as a submap and pose-graph global-consistency architecture rather than as a CoKo-style rendered-depth/camera-depth centralized loop-closure system.  Agents construct local Gaussian submaps; inter- and intra-robot loop closures provide constraints; and pose-graph optimization improves global consistency across submaps.  The available arXiv evidence does not by itself establish a single central server implementation, so the safest fusion-location wording is collaborative submap optimization with pose-graph global consistency.

The reported modality is RGB-D.  GRAND-SLAM is important because it extends beyond the small indoor two-agent setting common in Replica-style evaluations.  On Multiagent Replica, extracted tables report approximately 0.25 cm average ATE RMSE, 41.35 dB PSNR, 0.99 SSIM, 0.04 LPIPS, and 0.41 cm Depth L1.  On Kimera-Multi Outdoor, it evaluates six agents over approximately 1.85 km and reports about 4.99 m average ATE RMSE, with a corresponding rendering table around 27.44 dB PSNR, 0.97 SSIM, 0.11 LPIPS, and 1.39 Depth L1.  The reported hardware context includes two RTX 3090 GPUs.  Runtime, memory, and communication bandwidth evidence were not cleanly extracted; the paper evidence instead emphasizes accuracy, rendering quality, loop closure, and outdoor scale.

No credible public implementation was found in the available code searches.  GRAND-SLAM should therefore be cited as a strong paper-only benchmark and architecture reference for large-scale and outdoor multi-agent Gaussian SLAM.  Its caveats are mainly implementation availability and communication reporting.  For systems work, it motivates explicit evaluation axes for agent count, trajectory length, outdoor drift, inter-robot loop closure, and pose-graph constraints, but it does not yet provide an auditable software backend.

\paragraph{System profile.}
\textbf{Modality:} RGB-D.  \textbf{Map representation:} 3D Gaussian submaps / collaborative Gaussian reconstruction.  \textbf{Fusion architecture:} local submap optimization plus inter/intra-robot loop closure and pose-graph optimization.  \textbf{Source availability:} no public code found in the available searches; paper-only evidence.  \textbf{Benchmark highlights:} Multiagent Replica average ATE around 0.25 cm and PSNR around 41.35 dB; Kimera-Multi Outdoor six-agent evaluation over about 1.85 km with average ATE around 4.99 m.  \textbf{Caveats:} deployment/fusion location not fully established from accessible abstracts; limited runtime/memory/bandwidth reporting; no auditable code.

\subsection{MAGS-SLAM}
\label{sec:systems:mags-slam}

MAGS-SLAM is the most direct claimed RGB-only or monocular multi-agent 3D Gaussian Splatting SLAM system in the current candidate set \citep{mags_slam_2026}.  The project and arXiv evidence describe multiple monocular agents that build local Gaussian submaps using only RGB images, communicate compact submap summaries rather than raw observations or dense maps, verify cross-agent associations using geometry- and appearance-aware loop checks, and fuse local maps through occupancy-aware Gaussian fusion.  Its central technical challenge is monocular collaboration: unlike RGB-D systems, it must handle scale ambiguity while still producing a coherent global Gaussian reconstruction and per-agent trajectories.

MAGS-SLAM is therefore architecturally complementary to MAGiC-SLAM, CoKo-SLAM, and GRAND-SLAM.  Rather than assuming metric depth at every agent, it shifts the fusion contract toward compact monocular submaps, scale-aware alignment, and occupancy-aware Gaussian fusion.  The reported evaluation scope includes ReplicaMultiAgent, ReplicaMultiAgent Plus, ETH3D, Tanks and Temples, and 7-Scenes Fire.  However, in the evidence available here, these are project-page/arXiv claims rather than audited implementation results.  The fusion deployment location is also not fully resolved from the accessible text: the evidence supports a collaborative submap/fusion layer, but does not conclusively establish whether the implementation is centralized, distributed, or hybrid.

Source availability is the major limitation.  The public repository found for the project is website source, not implementation code, and the project page states that code and data will be released upon acceptance.  Consequently, MAGS-SLAM should be included as a target-class claimed system and as the leading monocular/RGB-only direction, but all code, runtime, and benchmark statements should be marked paper-only or project-page-only until an archival paper and implementation are available.

\paragraph{System profile.}
\textbf{Modality:} monocular RGB-only by core claim.  \textbf{Map representation:} local monocular Gaussian submaps and compact submap summaries fused into a global Gaussian reconstruction.  \textbf{Fusion architecture:} geometry/appearance loop verification plus occupancy-aware Gaussian fusion; central-vs-distributed deployment not fully resolved.  \textbf{Source availability:} promised only; website repo found, no implementation code.  \textbf{Benchmark highlights:} project/arXiv claims evaluations on ReplicaMultiAgent, ReplicaMultiAgent Plus, ETH3D, Tanks and Temples, and 7-Scenes Fire.  \textbf{Caveats:} project-page/paper-only evidence; no auditable code, license, runtime, or bandwidth data; benchmark claims should be treated as provisional.
```
